# 購入記録・結果・収支計算

## 1. 対象と前提

Milestone 5は実際の馬券購入を実行せず、外部で購入した内容を記録する。対応券種は単勝、複勝、枠連、馬連、ワイド、馬単、三連複、三連単。購入時オッズは参考情報であり、実払戻はJRA/NARの確定払戻表だけから計算する。

## 2. 購入記録

`purchases/{purchaseId}`は1回の購入操作を表し、`items[]`に券種、番号組、実購入額、任意の購入時オッズを保存する。同じ券種・番号組を複数回購入した場合も別の購入記録または別明細として保持する。購入額は100円単位、1記録の合計は1,000万円以下、明細は100件以下とする。

- `draft`: 更新可能な下書き。`revision`による競合検知を行う。
- `confirmed`: 確定済み。不変で、通常の更新・削除を禁止する。
- `corrected`: 訂正記録。不変で、`correctionOf`、`rootPurchaseId`、連続する`correctionSequence`を持つ。

訂正は元記録を上書きしない。集計時は同じ`rootPurchaseId`の最大`correctionSequence`だけを有効にするため、訂正前後を二重計上しない。購入プランと確定予想への参照は任意だが、設定時は不変スナップショットを参照する。

## 3. 結果と確定払戻

`results/{resultId}`は検証済み`ResultDocument`を`payload`として保持する。同着は同じ`rank`、取消・除外・競走中止は各status、返還は`payout_type=refund`として記録する。払戻・返還は100円当たりの公式金額と出典を必須とする。結果訂正も新規レコードとし、同じルートの最新版だけを採用する。

同一内容の二重登録は、正規化JSONのSHA-256から作る`contentHash`、決定論的`importId`、不変のimport logで拒否する。

## 4. 的中・返還・未判定

券種と番号組を確定払戻表へ照合し、次の順で判定する。馬単・三連単は順序を保持し、枠連・馬連・ワイド・三連複は番号を正規化する。

1. 同じ券種・番号組の公式`payout`があれば的中。
2. 同じ券種・番号組の公式`refund`があれば返還。
3. 同じ券種の公式払戻行が存在し、番号組がなければ不的中。
4. 結果未確定、同じ券種の払戻表がない、競合する公式行がある場合は未判定。

払戻金は`100円当たり確定払戻 × 購入額 / 100`、実現損益は`払戻金 + 返還額 − 購入額`、回収率は`(払戻金 + 返還額) / 購入額 × 100`。返還額は利益ではなく元本の返却として別表示する。一部でも未判定があればレース全体の損益・回収率は未判定とし、既知の払戻だけを参考表示する。

## 5. 台帳とtransaction

購入確定は負の`stake`、結果確定は正の`payout`を`bankrollTransactions`へ同一Firestore transactionで追加する。訂正は差額だけを`adjustment`として追加する。transaction IDとidempotency keyを決定論的にし、既存ドキュメントがあれば再実行を拒否する。通信失敗時は購入・結果・import log・台帳・レース状態の一部だけが残らない。

## 6. Security Rulesの範囲

Rulesは所有者、許可フィールド、主要型、ID、状態、配列件数、購入合計の基本範囲、100円単位、参照する確定予想・購入プランの存在、訂正チェーン、確定後の不変性を検証する。ただしRulesでは任意長配列の各明細合計、全払戻表の意味、予想候補との完全一致、台帳額の再計算を完全には検証できない。

Zod、純粋計算、repositoryのtransaction、Rulesを重ねるが、クライアントからの直接書き込みに対する完全な改ざん防止ではない。金銭管理を厳格化する場合はCloud Functions等の信頼できるバックエンドだけに作成権限を与え、サーバー側で全項目を再検証する。
