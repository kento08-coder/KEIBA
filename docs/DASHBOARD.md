# 成績・回収率・予想精度ダッシュボード

- 対象: Phase 1 Milestone 6
- 更新日: 2026-11-06
- 集計実装: `src/domain/calculations/dashboard.ts`

## 1. 集計単位

ダッシュボードはレース開催日を時系列の基準とし、購入記録の登録日では集計しない。購入は`rootPurchaseId`ごとに最大の`correctionSequence`だけを採用し、レースの`activePurchaseIds`がある場合はその有効ID集合と突合する。結果は`latestResultId`の確定・訂正版を優先し、参照がない場合だけ結果訂正チェーンの最新版を選ぶ。

結果未確定、同じ券種の公式払戻表不足、公式行の競合は`unresolved`（未判定）とする。不的中へ変換しない。未判定を含む収支は、現在判明している払戻・返還と全購入額から求めた暫定の現金収支として表示する。

## 2. KPI計算式

| KPI | 計算式・条件 |
|---|---|
| 総購入金額 | 有効購入明細の`stakeYen`合計 |
| 総払戻金 | 的中明細の確定払戻合計 |
| 総返還金 | 返還明細の返還額合計 |
| 実現損益 | `払戻金 + 返還金 - 購入金額` |
| 回収率 | `(払戻金 + 返還金) / 購入金額 × 100`。購入額0円は未算出 |
| 的中率 | `的中件数 / (的中件数 + 不的中件数) × 100`。返還・未判定は分母外 |
| 平均購入額 | 購入明細1件あたりの購入額 |
| 平均推定期待回収率 | 期待値を算出できる購入明細の算術平均 |
| 推定期待利益合計 | 購入時点の確率・観測オッズと実購入額による期待純利益の線形和 |

レース数はフィルター後に購入明細がある一意な`raceId`数、馬券件数は実購入明細数とする。同じ買い目を実際に複数回購入した場合は資金実績として各明細を数える。

## 3. 期待値と実績

期待値は次の順で不変スナップショットを参照する。

1. 購入が`sourcePlanId`と`sourceCandidateId`を持つ場合は、購入プランの`candidateSnapshot`
2. それ以外で確定予想と候補IDを持つ場合は、確定予想バージョンの候補
3. 参照できない場合は期待値未算出

確率・オッズ・観測日時を結果データから補完しない。実払戻は最新結果の公式払戻表だけを使う。推定期待利益と実現損益は意味が異なり、単一レースの上振れ・下振れを予想能力の証明とは扱わない。

## 4. 確率較正とBrier Score

確率帯は`0〜20%`、`20〜40%`、`40〜60%`、`60〜80%`、`80〜100%`。各帯で件数、平均推定確率、実際の的中率、その差を表示する。80〜100%帯だけ上端1.0を含む。

```text
Brier Score = mean((p - y)^2)
```

`p`は予想時の推定的中確率、`y`は的中1・不的中0。返還、未判定、確率なし、確定予想IDまたは候補IDなし、予想確定が購入以前と日時で確認できないデータを除外する。同じ`raceId + predictionVersionId + candidateId`を複数回購入しても、独立した予想回数として重複計上しない。値が小さいほど誤差は小さいが、少数標本では精度を断定しない。

## 5. 展開予想の振り返り

結果の`observed_pace.verified=true`かつペースが`unknown`でない場合だけ比較する。購入が参照した確定予想バージョンの全シナリオを使い、実際のペースと同じ`pace`を持つシナリオの発生確率を合算する。最大確率のシナリオだけで単純な正解・不正解にはしない。

現行スキーマには馬券候補ごとの展開別条件付き的中確率がないため、展開別の期待利益、全損確率、統計的な展開予測精度は算出しない。馬評価から数値を生成しない。

## 6. フィルター

- 開始日・終了日: レース開催日の両端を含む
- 主催者: 保存済みの値（JRA/NARを含む）だけを候補表示
- 競馬場: 保存済み`venueCode`だけを候補表示
- 券種: 全8券種または1券種
- 結果状態: 判定済み、未判定、すべて
- 購入プラン: `sourcePlanId`あり、なし、すべて

KPI、時系列、券種・主催者・競馬場表、期待値実績表、較正分析は同じ明細フィルターを使用する。台帳はレース単位のため、券種・結果状態・プラン有無で明細を部分抽出している間は台帳照合を行わない。

## 7. 台帳照合

明細を部分抽出していない場合、フィルター対象レースの`bankrollTransactions.amountYen`合計と、有効購入・最新結果から再計算した`払戻 + 返還 - 購入`を比較する。訂正差額と結果確定後の追加購入も台帳の全トランザクションを合算するため、過去版を新規購入として数えない。差額がある場合は、直接書き込み、欠損、移行前データなどを調査する必要がある。

## 8. Firestore読み取りと同期

`/users/{uid}/races`を開催日降順で購読し、各レースの`purchases`、`results`、`plans`、`predictionVersions`をリアルタイム購読する。台帳もユーザー単位で購読する。ログアウト時は購読を解除し、画面stateから個人データを除去する。Security Rulesの既存のUID分離を変更しない。

クライアント集計の読み取りコストを制限するため、Phase 1では最新200レースまでを対象とし、超過時は画面に表示する。明細表は先頭100件まで表示する。件数増加時は次の拡張を検討する。

- 期間別ページングと遅延購読
- Cloud Functions等による信頼できる集計キャッシュ
- 日・月・券種別の集約ドキュメント
- 集約更新の冪等性と原データからの再構築ジョブ

集計キャッシュを導入しても、不変の購入・結果・台帳を監査元として保持する。

## 9. UIとバンドル

分析ルートはReact Routerの`lazy()`で画面単位に遅延読み込みする。外部グラフライブラリを追加せず、累積収支はアクセシブルなSVG、棒グラフはCSSで描画する。スマホはカード、PCは横比較表を表示し、色だけでなく「的中」「未判定」「暫定」などの文字を併記する。

## 10. 制限と今後の候補

- ブラウザ集計はSecurity Rulesの代替ではない。
- 確率較正は購入した候補だけが対象で、全予想候補の母集団を表さない（選択バイアスがある）。
- 共同確率がないため、複数馬券のポートフォリオ分散や全損確率は算出しない。
- 競馬場名や主催者はコードから推測せず、保存値をそのまま表示する。
- 将来は全確定予想候補のアウトカム付与、展開別条件付き確率、信頼区間、標本数閾値、CSVエクスポートを検討する。
